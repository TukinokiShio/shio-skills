# 大纲 → Obsidian 笔记库（Outline → Obsidian Notes）

## 权限说明

| 声明的权限 | 实际用途 | 边界 |
| --- | --- | --- |
| `filesystem:read` | 读取用户提供的大纲素材；**只读地**读取用户既有笔记库以学习风格 | 只读，绝不写入既有库 |
| `filesystem:write` | 在**用户指定位置**新建目录、写入笔记/索引/模板文件 | 不覆盖用户既有文件；建库前先与用户确认位置 |
| `process:execute` | 运行自带的 `scripts/verify_notes.py` 做全库校验 | 只读文件、只打印结果，不修改任何文件 |

**本 skill 不联网、不发送任何数据到外部。**

## 用途

把一份**大纲**（课程目录、教材目录、考试大纲、章节清单、甚至一组截图）变成一套**可长期复习的笔记体系**：每一条大纲项对应一篇笔记，配索引层与双向链接，并遵循跨工具兼容的 Markdown 约定。

**默认产出形态是 Obsidian 笔记库（vault）**：`[[双链]]` + YAML 属性 + 图谱/反链是最大价值。同时严守"跨工具通用语法"约束，使同一份笔记在 Typora / VS Code / GitHub 里也不变形，且**笔记正文不依赖任何插件**。用户不用 Obsidian 时，就退化为一个结构良好的 Markdown 笔记库，流程完全不变。

与相邻 skill 的分工：`grill-me` 只追问、不落地；`obsidian` 只操作已有仓库；本 skill 负责**从大纲到成品库的完整交付**。

## 六条不可动摇的原则

1. **大纲即事实源，1:1 可追溯。** 一条大纲项 = 一篇笔记。文件名沿用大纲原文（保留其中的 `+`、括号、大小写、原有连字符），不"顺手规范化"。
2. **不擅自补章、不擅自合并。** 大纲的缺号、重号、怪编号一律**原样保留**，只在索引页显式说明。疑似缺漏**先核对再问**，不要自己补一节。
3. **先对齐再批量。** 永远先做一章样板 → 用户过目 → 再量产。批量产出 50 篇错稿的代价远大于产出 5 篇对的。
4. **每篇都必须有"推导"和"不确定性审计"两段——与学科、与用户水平都无关。**
   - **推导（第一性原理）**：不给结论，先给硬约束与反事实，把结论"推"出来。文科、医学、法律、语言同样推得动——只是约束换成了时代条件、生理机制、立法目的、交际需求（分学科写法见 `references/note-template.md`）。
   - **不确定性审计**：列常见误解、结论成立的**前提**、边界与反例、易混对比；对拿不准处**显式标注**（区分"已核实的事实 / 我的推断 / 未知"），不拿"大概""应该"冒充结论。
   - 这两段**不是可裁剪参数**：篇幅可以压到最短，但两段必须存在。缺了它们，笔记就退化成"把目录抄一遍"。
5. **不编造。** 知识点必须准确；不确定处显式标注（"此处按 X 教材通行说法，未经逐字核对"）。
6. **用户既有资产只读。** 可读地读取用户其他仓库以学习风格、并复制插件到新库；**绝不写入、绝不删改**。复制类操作用"读源写新"的方式（`cp`），完成后**验证源库未被改动**再报告。

## 阶段 0：先自己查，别问

在向用户提任何问题之前，**用只读手段把能自己回答的都答掉**：

- 列出工作目录与用户给的素材，确认大纲的真实形态（图片？文本？几份？）。
- 大纲是图片时：逐张读取并转录；**逐张做首尾衔接核对**（见阶段 2）。
- 查用户是否已有笔记仓库：读 Obsidian 的 vault 清单（Windows `%APPDATA%\obsidian\obsidian.json`；macOS `~/Library/Application Support/obsidian/obsidian.json`），或搜 `.obsidian` / `README.md` / `.git`。
- 定位到具体仓库时：读它的 `README`、目录结构、2–3 篇代表性笔记与 `.obsidian` 配置，**判断其既有风格与插件集**。

> 判据：**凡是"看一眼文件就能知道"的，绝不拿去问用户。**

## 阶段 1：追问（参考 `grill-me`）

按 `grill-me` 的做法：**先列出顶层决策分支 → 给出自己的推荐答案 → 再提问 → 只问不可自判的。**

**只问三类**（其余全部自己定并留痕）：
- 不可判定的歧义（事实层面推不出唯一解）；
- 权威冲突（两个同等权威的说法互相矛盾）；
- 缺失授权（涉钱、外部动作、不可逆操作）。

**技术方案一律自己定**：目录结构、文件名规范、frontmatter 字段、模板段落、交付批次、语法选择——自己推、说明理由，不占用用户注意力。

**通常只需 2–3 个问题**，每个都要带推荐项与"不回答时的默认处置"。可直接复用的问法、选项设计与五要素清单见 `references/grill-questions.md`。

## 阶段 2：大纲转录与缺漏核对

1. **逐项转录**大纲，统计**每章项数**与**总项数**。
2. **多图/多页时必做首尾衔接核对**：检查上一张的最后一项与下一张的第一项是否**紧邻**（无重叠、无跳号），逐条列出，例如 `2.1.6_2 → 2.1.6_3` 相邻、`3.1.5 → 3.2.1` 相邻。
   - **全部紧邻** ⇒ 素材完整 ⇒ 中间的编号空缺是**大纲本身真缺号**，不该问、更不能补；
   - **存在跳跃** ⇒ 素材不完整 ⇒ **必须先向用户确认**再动手。
3. **显式列出异常**：缺号、重复编号（同一编号出现两次）、标题被截断（如"最…"）。
   - 缺号/重号 ⇒ 原样保留，在索引页说明；
   - **标题被截断** ⇒ 可依该学科通行内容补齐，但**必须标注为推断**并请用户确认。
4. 把转录结果与项数统计**回显给用户**，使之成为双方共同的事实基础。

## 阶段 3：骨架 + 样板

1. **建骨架**：库根 + 章节目录 + 索引目录 + 模板目录 + 附件目录。结构见 `references/obsidian-layout.md`。
   - 用户已有仓库时：把新库建在**用户指定或归属明确的位置**，不污染其既有仓库；既有仓库只读。
   - 需要插件时：从用户已用的仓库**复制**（读源写新），复制后校验源库未被改动。
2. **写索引层**（防"信息坟场"）：1 个总览页 + 每章 1 个章索引。章索引**先列全部**笔记链接，当作进度路线图（未写的显示为未解析链接属正常）。
3. **写模板文件**：按 `references/note-template.md` 落一份可裁剪的模板，**其中第②段（推导）与第④段（不确定性审计）必须保留**。
4. **写第一章样板**（或前 5–8 篇）并**交给用户过目**。这是唯一必须停下等确认的点。
5. 统一语法约定：见 `references/markdown-compat.md`。**默认只用跨工具通用语法。**

## 阶段 4：分章批量产出

- **按章交付**；每章写完**立刻跑校验**，不把校验攒到最后。
- 每篇遵守模板的固定段落，且：表格优先于长段落；流程用 Mermaid 或编号步骤；**第②段必须真的在推导**（不是把结论换句话复述）；**第④段必须有具体的误判与前提**（不写"注意别记错"这类空话）；不确定处显式标注。
- **命名与链接一致性**：跨篇引用一律用双链，链接目标与文件名**逐字符一致**。
- 校验脚本：

```bash
python scripts/verify_notes.py "<库根目录>" --expect-notes 86
```

脚本检查：笔记总数与分章计数、**死链**、模板段落完整度、不兼容语法残留、代码围栏与折叠块配对、frontmatter 齐全性、篇幅区间。**任一项不通过就不要继续往下写。**

## 阶段 5：总校验与交付

1. 跑一次全库校验，把结果**如实报告**（含未通过项，不美化）。
2. 更新总览页的进度与结构说明。
3. 交付时说明：库在哪里、**用哪个工具打开哪个文件夹**、结构是什么、有哪些约定、还有什么没做。
4. **不要把"文件已创建"当成"任务完成"**——必须给出校验证据。

## 按情况裁剪（本 skill 的核心）

同一套流程，参数随场景变化。动手前先在心里填这张表：

| 维度 | 取值 | 影响什么 |
| --- | --- | --- |
| **学科类型** | 理工 / 文科 / 医学 / 语言 / 法律 / 商科 | 决定模板"现实关联"段的**名称与内容**（见 `references/note-template.md` 学科变体表），以及**推导段拿什么当约束、审计段从哪找误判** |
| **主要用途** | 在校跟课 / 期末突击 / 考研考公 / 职业考证 / 自学通识 | 决定**深度**（推导 vs 结论）、是否设"考点/题型"段、篇幅取向 |
| **已有环境** | 有仓库（含插件）/ 无仓库 / 有多个仓库 | 决定放哪、是否复制插件、是否新建 |
| **大纲形态** | 图片截图 / 文本目录 / 教材目录 / 网页 | 决定阶段 2 的转录方式与核对强度（图片必须做衔接核对） |
| **规模** | < 20 项 / 20–80 项 / > 80 项 | 决定交付节奏：一次做完 / 分章 / 分批且每批后确认 |
| **阅读工具** | 仅 Obsidian / 还需 Typora、VS Code、GitHub | 决定语法严格度（单一工具可放宽；跨工具必须严守白名单） |
| **对准确性的要求** | 考试/执业（严） / 泛读了解（松） | 决定"不确定标注"做到逐条还是整段 |
| **不裁剪的** | 第②段推导 + 第④段不确定性审计 | 上面怎么取值，**这两段都保留**（见原则 4） |

**通用判断法**：问自己"**若按默认方案做，最坏情况是返工还是不可逆损失？**" 返工 ⇒ 自己定并留痕；不可逆 ⇒ 停下来问。

## 常见误判（实战踩过的坑）

| 以为 | 实际 |
| --- | --- |
| "找到的那个仓库就是用户的" | 用户可能有多个仓库，你找到的可能只是空壳。**先看清单里哪个 `open: true`，并让用户确认** |
| "缺号说明截图不完整，得去问" | **先做首尾衔接核对**：紧邻即完整，缺号是大纲本身缺的——**不该问、更不能补** |
| "多写点更保险" | 单篇过长会让复习失效。**先与用户对齐篇幅，再谈加深** |
| "用某个工具的私有语法更好看" | 换到别的工具打开时会变成原文。**默认只用跨工具通用语法** |
| "文件名规范化一下更整齐" | 规范化会切断与大纲的 1:1 追溯，**破坏可核对性** |
| "文科/医学推不动第一性原理" | 推得动，只是约束换了：时代条件、生理机制、立法目的、交际需求（见 `references/note-template.md`） |
| "推导段就是写'为什么需要它'" | 那是复述结论。**必须有"没有它会出什么具体坏事"这一步** |
| "审计段写'注意别记错'就够了" | 空话无价值。**要写出具体的误判，以及结论只在什么前提下成立** |
| "文件建完了就是做完了" | 没有校验证据就是没做完。**死链、段落缺失、语法残留都要跑脚本确认** |
| "对话里说过了就等于记下了" | 约束只写在日志里会被压缩掉。**长期约定当场写进项目的常驻记忆或规则文件** |

## 配套资源

- `references/grill-questions.md`：追问清单（问什么、怎么问、推荐答案、不答怎么办）。
- `references/note-template.md`：七段笔记模板 + 学科变体表 + **第一性原理/不确定性审计的分学科写法** + 好/坏写法对照。
- `references/obsidian-layout.md`：目录结构、索引层设计、插件处理、命名与 frontmatter 约定。
- `references/markdown-compat.md`：跨工具语法白名单/黑名单与实测结论。
- `scripts/verify_notes.py`：全库校验脚本（可直接运行，支持自定义期望项数）。

## 相关 skill
